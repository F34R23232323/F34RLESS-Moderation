Required prefix-only commands:

Safe reversal workflow:

1. Parse and validate the exact transaction ID.
2. Load the immutable original transaction and all related ledger entries.
3. Verify it belongs to the current guild and is an eligible reversible type.
4. Reject already reversed, superseded, expired, unresolved, cross-guild, system-migration, initial-seed, destructive-reset, or otherwise unsafe transactions.
5. Calculate a dry-run compensation plan showing every affected account, item, role, fee, tax, stock value, and expected balance/result.
6. Detect conflicts such as spent funds, consumed/transferred items, changed ownership, deleted roles, completed downstream marketplace trades, or insufficient balances.
7. Send an admin-only Components V2 preview with warnings and a short-lived single-use confirmation token bound to guild, administrator, transaction, plan hash, and expiry.
8. Require the separate prefix-only confirmation command. A button may cancel or inspect the preview but must not perform the final reversal.
9. Re-check permissions, eligibility, balances, inventory, plan hash, and current versions at confirmation.
10. Execute the complete compensation atomically and idempotently.
11. Append new compensating ledger entries referencing the original transaction. Never edit or delete the original ledger entry.
12. Mark the reversal relationship/status, invalidate the token, send a receipt, and dispatch high-severity staff logs.

Each reversal requires a non-empty staff reason with sensible length limits. Store the initiating admin, confirming admin where different, reason, original transaction ID, reversal transaction ID, timestamps, affected entities, before/after values, validation results, and source message/channel IDs.

Define eligible behavior per transaction type rather than using one generic balance subtraction. For example:

- payments: debit the recipient and credit the sender only if safe, respecting configured debt policy
- purchases: return currency and remove/return the exact items, restore stock where valid, and handle consumed items as a conflict
- marketplace purchases: compensate buyer/seller/item escrow/fees as one plan, blocking reversal when ownership has moved again unless a dedicated safe resolution exists
- trades: reverse every exchanged item and currency entry together or refuse; never partially corrupt a trade
- stealing: return stolen funds and undo the related fine only according to the original entries
- role rewards: remove/refund only if the role and reward state can be safely reconciled
- staff adjustments: create the opposite adjustment with complete attribution
- claims/rewards: revoke only unspent/recoverable value unless the guild explicitly permits bounded negative balances

Do not silently force a negative balance. By default, insufficient funds or missing assets must block the reversal and show the exact conflict. If the guild enables economy debt, enforce a separately configured debt floor and flag the account. Provide no `--force`, `--skip-checks`, or similar unsafe bypass flag. Complex cases should be resolved through audited admin adjustments rather than corrupting ledger invariants.

The dashboard MUST display reversal status, history, plans, and audit evidence and MUST contain secure Reverse, Confirm Reversal, and Cancel Reversal buttons for authorized administrators. These actions must use the same central preview, conflict detection, compensation-plan, ledger, and idempotency services as the prefix commands.

Dashboard reversal workflow:
